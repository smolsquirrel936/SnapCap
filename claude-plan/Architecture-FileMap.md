# SnapCap — Architecture & File Map

## Context

This document explains **what each file does** and **how the files interact**. It makes the
layered architecture from `Tech-Stack-Plan.md` concrete at the file level, and complements
`Implementation-Plan.md` (which says *when* each file is built, in which stage).

Status legend: **✅ exists now** (with the stage or feature that built it: `S0`–`S7` roadmap
stages, `OCR-S*`, `REC-*` recording phases, `SCR` scrolling capture, `QR` barcode) · **⤷ folded /
superseded** (the planned file never existed; its job lives in the named file) · **✖ won't build**
(dropped by decision — kept as a row so it is not planned again).

## Dependency rule (read this first)

Dependencies point **inward only**:

```
        app/                (composition root — wires everything)
          │  creates & owns
          ▼
   ui/  ──uses──▶  core/  ──uses──▶  platform/  (interfaces only: platform.h)
                                          ▲
                                          │ implements
                                   platform/win/  (concrete Win32 backends)
```

- `core/` is **platform-agnostic** and **UI-agnostic** — it never `#include`s `ui/` or
  `platform/win/`; it talks to hardware only through the abstract interfaces in
  `platform/platform.h`. This is what keeps it portable + unit-testable (`Tech-Stack-Plan.md`
  "Target architecture").
- `ui/` may use `core/` and the `platform.h` interfaces, never `platform/win/` directly.
- `app/` is the only place that knows the concrete backend exists: it calls
  `platform::createPlatform()` and injects the result downward.
- `lang/` and `res/` are **data, not code** — loaded at runtime, editable without recompiling.

## How they interact — primary flows

### A. Startup & wiring (`app/` is the only integrator)
```
main() ─▶ QApplication
       ─▶ I18n.load(lang/) , setLocale(settings.locale)
       ─▶ Application
            ├─ Settings(config.ini)
            ├─ platform = createPlatform()        // win backend bundle
            ├─ ActionRegistry  ◀─ load res/keymap.default.yaml + user overrides
            ├─ platform.hotkeys.register(F1/F3/…) ─▶ dispatch(ActionId)
            └─ TrayIcon(actions, i18n)
```

### B. Snip (F1) — command bus + inward dependencies
```
WinGlobalHotkey(WM_HOTKEY) ─▶ ActionRegistry.dispatch(Snip)
   ─▶ Application's Snip handler
        ─▶ IScreenCapture.grabVirtualDesktop()        // platform/win
        ─▶ SnipOverlay(frozen image)                  // ui, owns SelectionModel
             ├─ IElementDetect.elementAt() ─▶ SelectionModel.suggest()
             ├─ SnipScreenView loupe ◀─ SelectionModel.changed(), ColorPicker
             └─ on finish key (SnipOverlay::onKey — hardcoded, not dispatched)
                  ─▶ IClipboard.setImage() / ImageExport.toFile()   // platform / core
                  └─ (Pin) ─▶ pin sink ─▶ PinManager.addImage()
```
Note the direction: `ui/SnipOverlay` calls **interfaces** (`IScreenCapture`,
`IElementDetect`, `IClipboard`) — never `platform/win` directly. `core/SelectionModel`/`ImageExport`
know nothing about widgets.

### C. Paste/Pin (F3)
```
dispatch(Paste) ─▶ ClipboardContent.classify(QMimeData)        // core
   ─▶ PinManager.pin(content)                                  // core, owns models
        ─▶ PinWindow(PinModel)                                 // ui
             └─ WinPinSurface: always-on-top / click-through / opacity   // platform/win via IPinSurface
   recover ring / hide-all / magnetic snap live in PinManager (core).
```

### D. i18n live switch (proves "strings out of code")
```
PreferencesDialog(language dropdown) ─▶ I18n.setLocale("zh_cn")
   ─▶ I18n.localeChanged()  ──▶  each connected widget's retranslate() re-applies t(key)
TrayIcon / PreferencesDialog / ColorDialog / GroupManagerDialog rebuild labels from keys.
No literal strings anywhere.
```

### E. Settings & hotkey remap
```
PreferencesDialog ─▶ Settings.set("hotkey/snip","Ctrl+F1")
   ─▶ ActionRegistry.bindKey(Snip, …) ─▶ WinGlobalHotkey re-register
Settings.changed(key) lets any component react (e.g. quick-save dir).
```

## Why this shape (ties to `Tech-Stack-Plan.md`)

- **Portability:** only `platform/win/*` is OS-specific; a future `platform/mac` implements
  the same `platform.h` and `createPlatform()` — no `core/`/`ui/` changes.
- **Testability:** `core/` has no Qt-widget or Win32 dependency, so the high-value logic
  (selection math, annotation doc, clipboard classify, history) runs in headless QtTest.
- **i18n out of code:** all user-facing text flows through `I18n` + `lang/*.yaml`;
  `tools/i18n_check.py` is the enforcement mechanism (every key used in code must exist in
  `en.yaml`).
- **One command bus:** the Action layer means global hotkeys and the tray are the same
  dispatch path — the basis for remapping. In-overlay and in-pin keys are handled directly by
  their widgets and are not remappable.
